# 에이전트의 서버 성능 검사 지침

서버 성능 검사·병목 조사·개선 전후 비교를 수행하는 에이전트는 이 문서를 따른다.
필요한 값을 기존 도구와 서버에서 직접 조회하고, 부족한 관측 기능과 시나리오는 가능한 한 Server Lab에 추가해 다음 검사에서도 재사용한다.
현재 API·시나리오·지표의 상세 계약은 [Server Lab](../development/SERVER_LAB.md), 개선 과제는 [작업 목록](../../tasks/todo.md)의 54·62번을 참조한다.
이 문서는 검사 절차와 확장 기준이다. 아래의 추가 후보가 이미 구현되었거나 성능 측정이 완료되었다는 의미는 아니다.

## 검사 시작 전

1. 검사할 동작·병목 가설·비교 지표·성공/실패 조건을 정하고 `tasks/todo.md`에 계획을 기록한다.
2. 현재 구현·관련 테스트·알려진 문제를 확인한다. 기능 오류가 부하를 줄여 빨라 보일 수 있으므로 의도한 동작이 수행되는지 먼저 확인한다.
3. 전용 `LOCAL_TEST`·DB 없는 서버를 기본으로 사용한다. 외부 클라이언트·다른 실행과 매칭 참가자가 섞이지 않도록 한다.
4. 빌드 구성·소스 상태·환경·계측 설정·시나리오·seed·부하 조건과 워밍업/측정/종료 구간을 기록한다.
5. 필요한 정보의 존재·단위·출처·수집 주기·보존 범위부터 확인하고, 정보가 부족하면 아래 확장 절차를 진행한다.

기본 성능 비교는 같은 환경의 x64 Release로 수행한다. Debug의 진단 결과와 Release 성능 수치를 섞지 않는다.
소스 commit과 미커밋 diff 식별값, 실행 파일·시나리오·CSV/지형 등 영향 데이터의 hash, OS/CPU/논리 코어 수와 Python 버전을 함께 남긴다.
더미/monitor의 CPU·메모리·송수신 처리도 확인해 부하 생성기나 관측 도구의 포화를 서버 한계로 해석하지 않는다.

## 먼저 조회할 정보

같은 PC에서 실행 중인 monitor의 기본 주소는 `http://127.0.0.1:8790`이다. 현재 지원 API는 다음과 같다.
원격 에이전트의 localhost는 다른 PC를 가리킬 수 있으므로 실행 위치를 확인한다.

| 출처 | 현재 확인 가능한 정보 | 해석 시 주의 |
|---|---|---|
| `GET /api/state` | CPU·메모리·네트워크·Core 자원·작업 지표·최근 시계열, 현재 실행/단계 판정·결과 ID | 소켓 수는 접속자 수가 아니며 queued/running은 근사 순간값 |
| `GET /api/world` | 실행에 속한 더미/NPC 좌표·궤적·HP·관측 사건·매치 일정 | 더미가 수신한 범위이며 서버 전체 월드·AI FSM/타깃이 아님 |
| `GET /api/scenarios` | 사용 가능한 시나리오와 행동·기본 조건 | 요청 부하와 실제 완료 부하를 따로 확인 |
| `GET /api/terrain?map=lobby` 또는 `map=game` | 높이 영상·NavMesh·원본 범위/hash·로비 고정 NPC | 로비 NPC는 클라이언트 고정 배치이며 서버 실시간 상태가 아님 |
| `GET /api/result?id=<run_id>&format=json` 또는 `format=csv` | 저장된 assertion·시계열·종료 world(JSON), assertion(CSV) | 전체 시간 월드 snapshot/리플레이는 없음 |
| `artifacts/logs/server-lab/metrics/*.json` | reporter의 원본 계측 snapshot | 최신 파일 교체 방식이므로 장기 기록의 대체가 아님 |
| 서버 종료 로그 | 종료 코드·`pending=0 sockets=0 leased=0` 등 회수 결과 | reporter의 stopped만으로 자원 회수 성공을 판정하지 않음 |

```powershell
$state = Invoke-RestMethod http://127.0.0.1:8790/api/state
$world = Invoke-RestMethod http://127.0.0.1:8790/api/world
$state.servers | ConvertTo-Json -Depth 10
$world.timelines | ConvertTo-Json -Depth 10
```

API와 저장 결과의 수치로 판정하고 화면은 위치·추세·이상 구간을 확인하는 데 사용한다.
표본의 instance·시각·수집 지연·종료 여부를 확인한다. 누락·미수집·stale은 0이나 정상 값으로 대체하지 않는다.
현재 단계 p50/p95/p99는 준비·대기를 포함한 성공 단계 완료 시간이며 네트워크 RTT가 아니다. 실패/timeout 비율도 함께 보고한다.
CPU는 전체 논리 코어 수로 정규화한 프로세스 사용률이다. 특정 worker의 포화는 별도 관측이 필요하다.

## 정보가 부족할 때 도구에 추가하는 기준

조회할 수 없다는 이유로 필요한 검증을 생략하지 않는다. 기존 계측/API/결과 형식을 먼저 확인하고, 검사의 근거가 되는 정보를 지속적으로 조회할 수 있도록 확장하는 것을 기본으로 한다.

1. 누락된 값과 그 값으로 판정할 질문을 기록한다. 예: enqueue 대기 p99가 없어서 작업 큐의 기아를 확인할 수 없음.
2. 실제 상태를 소유한 서버 실행 경로에서 측정할지, 더미 응답에서 계산할지 정한다. 관측값·추정값·서버 확정값을 구분한다.
3. 서버의 선택 활성화 계측 → snapshot → monitor API → 저장 결과까지 필요한 경로에 추가한다. 반복 검사에 필요한 값은 일회성 출력이나 그래프에만 두지 않는다.
4. 이름·단위·시계 기준·집계 구간·샘플 수·누락/오버플로·보존 상한·재시작 초기화·schema 호환성을 명시한다.
5. 비용과 정확성을 검증한다. 계측 켬/끔의 같은 부하 비교, 오류/수집 실패·재시작·동시 접근·종료 검사를 포함한다.
6. 관련 자동 검사·사용 문서·작업 목록을 갱신한다. 구조나 흐름이 변경되면 프로젝트 Archify 지침도 적용한다.

별도 reporter가 가변 게임 객체를 직접 순회하지 않도록 한다. 상태 소유 경로에서 안전한 복사본을 만들고 별도 경로에서 직렬화·파일/HTTP I/O를 수행한다.
고빈도 작업은 카운터·제한된 histogram/버퍼 등으로 집계해 측정 비용을 제한하고, 샘플링 여부와 버린 값의 수를 기록한다.
게임 wire·게임 규칙·기존 동시성 경계를 관측 편의만으로 바꾸지 않는다. 이름·계정·토큰 등 민감한 원본 식별값은 결과에 넣지 않는다.

현재 구현에 없는 대표적인 확장 후보는 다음과 같다. 실제 검사 목적에 필요한 항목부터 추가한다.

| 검사 목적 | 추가할 정보 후보 |
|---|---|
| JobQueue 병목·공정성 | enqueue→실행 대기 분포, 작업 종류/대상별 완료 수·대기 시간, 재등록 수·최장 대기 |
| 게임 업데이트 지연 | tick/업데이트 실행 시간과 간격 분포, 목표 시각 초과 수·초과 시간 |
| 실제 수용 부하 | 서버 확정 접속자·진행 매치·활성 NPC 수, 요청/수락/완료/실패 처리량 |
| 부하 생성기 한계 | 요청 예정/실제 전송 시각 차이, 더미 수신 backlog·CPU·누락/실패 수 |
| 종료 후 비용 | 활성 매치/타이머·전송 수·자원 수의 종료 전후 변화, idle 기준 복귀 시간 |
| 장시간 비교 | 측정 구간 전체 시계열·histogram·환경/소스 식별값의 저장 및 조회 |

기존 도구로 추가하기 어려우면 프로파일러/ETW 등 목적에 맞는 도구를 함께 사용하고 재현 명령·결과 경로를 남긴다.
추가가 불가능하거나 비용이 큰 항목은 이유·대체 근거·판정 제한을 명시하고 후속 과제로 등록한다. 없는 정보를 추정해 검증 완료로 보고하지 않는다.

## 검사 목적에 맞는 시나리오 추가

성능 검사마다 기존 시나리오의 적합성을 검토하고, 필요한 동작·부하·지속 시간이 없으면 `tools/server_lab/scenarios`에 재사용 가능한 시나리오를 추가한다.
단순히 더미 수만 늘리는 것으로 목적에 맞는 부하가 만들어졌다고 간주하지 않는다.
새 시나리오에는 목적·전제 조건·참가자/매치 수·역할·행동 순서·시간·seed·기대 응답과 timeout/실패 조건을 명시한다.
반복 가능한 워밍업·측정·정리 구간과 요청/완료 부하를 정의한다. 현재 runner가 구간이나 요청 주기를 표현하지 못하면 필요한 runner/API/결과 계약을 먼저 확장한다.

| 목적 | 기존 출발점 | 필요에 따라 추가할 시나리오/판정 |
|---|---|---|
| idle 비용 | 서버 지표 | 접속자 0·접속 후 대기·전원 종료 후 대기를 분리하고 CPU/큐/전송 복귀 확인 |
| 연결 생명주기 | `lobby-cycle` | 반복 접속/종료·재접속·급격한 변동, 중복 정리/누수/실패율 확인 |
| 이동·작업 공정성 | `lobby-movement`, `match-actions` | 지속 이동과 정지/제어 요청 혼합, 대상별 응답 지연·기아 확인 |
| 다중 매치 확장 | `match-actions`, `world-watch` | 4/8/16/32명 단계별 동일 행동, 실제 매치 분리·완료 부하 확인 |
| NPC·주기 이벤트 | `world-watch`, `timeline-watch` | 미니언 경로 이동/재스폰·복수 웨이브·게이트 해제 전후 부하 구간 확인 |
| 근거리 전투 | 후속 확장 필요 | 실제 타깃 접근·이동/공격·애니메이션 완료 ACK·피해/사망 판정까지 조건 구성 |
| 장시간 안정성 | 후속 확장 필요 | 반복 매치·종료·취소 후 재실행, 메모리/타이머/전송 누적과 전체 기록 확인 |

이 표는 검사 설계 후보이며 자동으로 모두 지원하거나 통과한다는 뜻이 아니다.
현재 runner는 최대 32명, match는 4의 배수, 행동 1~100개·행동 시간 최대 120초이며 `move/stop/skill/wait/reconnect`를 지원한다. reconnect는 lobby 전용이다.
match 준비는 4명씩 순차 수행하므로 현재 방식의 결과를 동시 로그인 폭주 성능으로 보고하지 않는다.
일반 몬스터는 근처 타깃이 없으면 대기할 수 있지만 미니언은 자율 경로 이동이 필요하다. 스킬 승인 응답만으로 실제 전투 부하가 재현되었다고 판단하지 않는다.
현재 더미는 NPC 애니메이션 완료 ACK를 자동 전송하지 않는다. 전투 부하 검사에는 해당 흐름의 지원과 판정을 추가해야 한다.

새 시나리오는 schema·잘못된 입력·실패/timeout·취소·연결 정리와 실제 서버에서의 의도한 동작을 검증한다.
측정을 통과시키려고 timeout이나 assertion을 완화하지 않는다. 기존 로비 이동 timeout과 종료 매치 전송 누적도 결과에 포함한다.
부하의 발행 주기와 대기 방식을 명시하고, 응답을 기다려 다음 요청을 보내는 방식이 서버 지연 시 발행량을 줄인다는 점을 반영한다.
서버 시간 기반 이벤트는 서버 확정 상태와 수집 시각으로 확인하고, 다른 프로세스의 시각을 단순히 빼서 지연으로 계산하지 않는다.

## 측정·비교·보고

1. 같은 조건의 사전 기능 검사와 워밍업을 거친 뒤 지정한 구간만 성능 집계에 사용한다. 시작/준비·정리 구간은 별도 보고한다.
2. 개선 전후 동일 시나리오/hash·계측·참가자/입력 주기·seed 묶음·시간·반복 횟수로 실행한다. 기본 5회 이상을 목표로 하고 예외 사유를 기록한다.
3. 가능한 한 전후 실행 순서를 번갈아 환경 변화를 줄인다. 매번 기존 서버/매치/타이머 상태를 초기화하고 같은 시작 조건을 확인한다.
4. 처리량·성공/실패율과 지연 분포를 함께 비교한다. CPU/메모리가 줄었어도 요청 누락·기아·NPC 정지가 발생하면 개선 성공으로 판단하지 않는다.
5. p50/p95/p99는 샘플 수·단위·구간을 명시한다. 평균값으로 꼬리 지연을 대신하지 않으며 여러 실행의 percentile을 단순 평균해 전체 percentile로 표시하지 않는다.
6. 각 실행 원시 결과와 요약을 저장하고 반복 간 중앙값·범위 등 변동을 보고한다. 실패 실행은 삭제하거나 조용히 제외하지 않는다.
7. 종료 코드·더미 연결 0·Core 잔여 자원·종료 후 idle 복귀를 확인한다. 비교용 자동 기준과 미달 여부를 결과에 남긴다.

현재 monitor의 화면 시계열은 최근 120개, 실행 결과의 서버 표본은 최대 3,600개다. 월드 궤적도 제한되어 있다.
장시간 측정에서 필요한 구간이 잘리지 않도록 시작 전에 보존 범위를 확인하고, 부족하면 제한된 크기의 분할 저장/집계와 조회 기능을 추가한다.
현재 결과에는 명시적인 워밍업/측정 구간·대상별 공정성·tick histogram·비교 보고서가 완비되어 있지 않다.
기능 회귀 통과와 기준 벤치마크/성능 개선을 구분하며, 아직 추가하지 않은 측정 기능을 사용했다고 기록하지 않는다.
