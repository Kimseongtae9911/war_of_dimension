# Visual Studio 2026 마이그레이션

## 적용

- 설치된 Visual Studio 2026 `18.10.12217.157`, MSVC `14.51.36231`/v145 환경을 사용했다.
- C++ 프로젝트 8개의 `PlatformToolset`을 v145, `VCProjectVersion`을 18.0으로 갱신했다. 기존 솔루션 8개의 Visual Studio 메타데이터도 18로 맞췄다.
- `NewWod.slnx`에서 핵심 클라이언트·로비 서버·게임 서버를 함께 연다. 기본 검증 configuration은 Debug/Release x64다.
- `Directory.Build.props`에 핵심 모듈 출력·중간 경로와 debugger 작업 디렉터리를, `Directory.Build.targets`에 공통 include·FMOD 링크 경로·런타임 복사를 정의했다. CLI와 VS가 같은 설정을 사용한다.
- 핵심 모듈의 CP949 소스 19개와 UTF-16LE 리소스 스크립트 1개를 UTF-8로 변환했다. CP949 decoding은 오류 대체 없이 엄격하게 수행하고 원문 round trip과 변환 후 텍스트 일치를 확인했다. UTF-16LE는 BOM을 확인해 별도로 해석했다. 바이너리 에셋은 변환하지 않았다.
- C++ compiler에 `/utf-8`을 적용해 OS별 기본 코드 페이지에 의존하지 않게 했다. C++20, 패킷 형식과 게임 규칙은 유지한다.

## 사용

`NewWod.slnx`를 Visual Studio 2026에서 열고 x64 configuration을 선택한다. VS에서 빌드해도 FMOD DLL이 실행 파일 옆으로 복사된다. debugger 작업 폴더는 각 모듈의 원본 폴더다.

클라이언트를 디버깅할 때 먼저 `scripts/Start-Local.ps1 -ServersOnly`로 두 서버를 준비하고 VS에서 클라이언트를 시작한다. 서버 연결 순서를 보장하는 전체 실행은 [개발 환경](SETUP.md)의 스크립트를 사용한다.

## v145 도구를 찾지 못하는 경우

VS2022로 이 솔루션을 빌드하면 설치된 환경에서 `MSB8020`이 발생한다.
VS2026이 설치돼 있어도 VS2022에서 연 솔루션은 VS2022의 MSBuild를 사용한다.
`NewWod.slnx`를 Visual Studio 2026에서 열어 빌드한다.
파일 연결이 VS2022를 가리키면 다음 명령으로 IDE를 지정한다.

```powershell
& 'C:/Program Files/Microsoft Visual Studio/18/Community/Common7/IDE/devenv.exe' "$PWD/NewWod.slnx"
```

CLI에서는 `./scripts/Build.ps1 -Configuration Debug`가 VS2026의 MSBuild를 선택한다.
2026-10-07에 전체 Debug x64 빌드는 통과했고, VS2022의 `PrepareForBuild`에서는 같은 오류를 재현했다.
프로젝트의 v145 설정은 유지한다.

## 검증 범위

통합 개발 이후 루트 솔루션은 `dotnet sln NewWod.sln migrate`로 XML 기반 `.slnx`로 전환했다. 프로젝트 3개·솔루션 폴더·개발 파일과 x64 Debug/Release 설정을 유지한다. 기존 루트 `.sln`은 제거하고 서버 filter의 solution 경로도 갱신했다. 공유 실행 프로필은 내용 그대로 `NewWod.slnxLaunch`로 이전했다. 개별 모듈의 기존 `.sln`은 호환 진입점으로 남겨 둔다.

형식 전환은 [Microsoft SLNX 안내](https://devblogs.microsoft.com/visualstudio/new-simpler-solution-file-format/)와 [dotnet sln migrate 문서](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-sln#migrate)를 따른다. launch 파일이 자동 이전되지 않는 점은 [SDK 저장소 기록](https://github.com/dotnet/sdk/issues/48014)을 참고해 명시적으로 처리했다. `.slnx`도 Visual Studio의 MSBuild로 C++를 빌드하며 `dotnet build`로 C++ toolchain을 대신하지 않는다.

SLNX 전환 후 `Build.ps1`의 전체 Debug·Release 빌드와 Debug 서버 filter 빌드를 확인했다. 서버 filter 로그에 클라이언트 프로젝트가 포함되지 않는 것도 검사했다. 프로젝트·개발 파일 경로와 기존 launch JSON 내용이 일치한다. Visual Studio GUI의 프로필 선택·F5 실행은 직접 점검하지 않았다.

핵심 3개 모듈의 Debug/Release x64 재빌드와 로컬 시작을 확인했다. 남겨 둔 실험·스트레스 테스트 프로젝트는 toolset 메타데이터를 갱신했으나 해당 프로젝트의 빌드·실행 전체를 검증한 것은 아니다. x86도 검증 범위가 아니다.

기존 코드에는 narrowing·signedness·미사용 변수 등의 warning이 있다. toolset 이전을 위해 경고를 비활성화하거나 데이터 타입·게임 동작을 일괄 변경하지 않았다. `artifacts/logs/build-*.log`에서 확인하고 별도 코드 리팩토링으로 처리한다.

Microsoft의 [C++ 업그레이드 안내](https://learn.microsoft.com/en-us/cpp/porting/upgrading-projects-from-earlier-versions-of-visual-cpp?view=msvc-170)와 [2015–2026 바이너리 호환성 문서](https://learn.microsoft.com/en-us/cpp/porting/binary-compat-2015-2017?view=msvc-170)를 기준으로 toolset과 실제 빌드·실행을 함께 확인했다. FMOD import library와 DLL을 유지했고 현재 x64 링크·시작 결과로 호환 범위를 확인한다.
