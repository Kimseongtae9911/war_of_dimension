보상 기록을 디스크에 확정한 이후의 재처리를 보호한다. 수신 원본의 고유 ID·ACK가 없는 기존 프로토콜, 디스크 확정 전 강제 종료, 운영 DB·블록체인·GUI 조작은 이번 보장 범위에 포함되지 않는다. PBKDF2와 기록 flush의 추가 비용은 존재하며 최대 처리량은 미측정이다.

실패·정체의 보존 경계 부재

보상은 메모리에만 있었고 paused 세션 입력에는 상한이 없었다. 종료 도구가 15초 후 서버를 강제 종료할 수 있었으며 비밀번호는 평문이었다.

해결 방식

세션 예약 → 입력 상한 → SQL 전용 FIFO → DB 확정 잔액·rowversion → 세션 완료
보상 수신 → 전용 기록 worker → flush·작업 ID → SQL 원장 트랜잭션 → 기록 삭제

만료 삭제와 재고 반환은 한 트랜잭션으로 묶었다. 계정당 소유 연결을 하나로 제한하고 BalanceVersion이 오래된 결과는 적용하지 않는다. 세션 입력은 256건·65,536 bytes로 제한하며 완료와 cleanup은 별도로 통과한다.

기록 worker가 디스크 I/O를 담당하므로 로비 잠금에서 파일 flush를 기다리지 않는다. 종료는 기록 worker join → DB drain 순서다. SQL 실패 기록은 다음 시작에 재생하고 reward_applied.Operation_ID로 같은 기록의 재적용을 막는다. 비밀번호는 salt 16 bytes·hash 32 bytes의 PBKDF2-HMAC-SHA256 600,000회로 저장하며 계산은 DB worker에서 실행한다.

record = journal.Append(account, delta); // write + flush + promote

추가 검사에서 구매/만료 경합 4회/구성 모두 아이템1개·합계4000 Token을 유지했다. 400건 입력 flood는 상한 초과 후 연결을 닫고 소유권을 해제해 재접속했다. 1초로 줄인 종료 대기 한도에서도 살아 있는 프로세스와 실행 기록을 유지했고, SQL 잠금 해제 후 정상 drain·자원0을 확인했다.

보상17 Token의 수신부터 온라인 잔액 통지까지 관측값은 Debug 17.563 ms, Release 16.092 ms이다. 각1회·루프백·낮은 부하의 관측이며 p99나 서비스 처리량을 뜻하지 않는다. 기본 PBKDF2 비용을 포함한 로그인 지연의 별도 전후 측정은 하지 않았다.

계정 비밀번호의 평문 이전과 잘못된 형식의 이전 실패 rollback을 검증했다. 새 스키마 v3·18개 프로시저 준비 및 반복 실행을 확인했다. 기존 전체 빌드 경고가 해소됐다고 주장하지 않는다. 새 검증의 모든 서버는 정상 종료했고 pending/sockets/leased=0이다.
