수정 전 실행 파일을 보존해 같은 Release 조회를 비교했다. 지연은 전후 각각200건×5회, SQL 수는 별도100건의 Extended Events로 확인했다. 장애 복구는 구성별5회 반복과 실패/만료/종료 경계를 재검증했다.

2. 분석한 원인

기존 구현은 DB 작업마다 SELECT 1을 실행했다. 실제 조회가 한 번인 요청도 별도의 SQL 왕복과 결과 처리를 거쳤다. 사전 확인 성공 직후에도 단절될 수 있으므로 실행 실패 정책을 대체하지 못했다.

이전: 매 작업 사전 확인
return database.Probe();
// Probe 내부
ExecuteDirect(L"SELECT 1");
수정: 정상 상태 바로 실행
try {
    work.m_execute();
    Finish(work);
} catch (...) {
    // 이 경로에서만 _connectionLost() 호출
}

3. 해결 방식

큐의 probe 콜백과 CDataBase::Probe를 제거했다. 실제 SQL이 실패하면 오류와 연결 상태를 진단해 재접속 상태로 전환한다. 연결 생성·스키마·DB 식별값 검증을 통과한 뒤 FIFO를 재개한다.

5. 추가 발견한 결함 또는 대응 필요 요소

항목영향·현재 상태다음 대응
첫 요청의 쓰기 단절사전 probe가 없으므로 첫 쓰기가 실패할 수 있다. 결과 불명확 시 자동 반복하지 않음요청 ID·일반 쓰기 원장으로 처리 여부 확인 지원
검증 fixture예전 검사는 사전 probe가 첫 구매를 보호한다고 가정. 안전한 조회 실패 뒤 미실행 구매 대기와 첫 쓰기 실패를 나누어 재검증보장 경계에 맞는 실패 주입 유지
원격 DB·병렬 부하이번 수치는 로컬 순차 읽기. 최대 처리량과 WAN 비용 미측정실사용 부하에서 큐/SQL/네트워크 시간을 분리 측정
내구성과 인증보상만 디스크 보존. 일반 요청 원장·원본 보상 ACK·운영 전송 인증은 기존 후속 과제업무 계약에 맞춰 별도 설계

측정 근거: Microsoft Extended Events. 운영 DB·전원/디스크 장애·전체 GUI는 검증하지 않았다.
