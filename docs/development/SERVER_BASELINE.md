# 실제 서버 JobQueue 최적화 전 기준 측정

2026-10-11, `codex/jobqueue-optimization`에서 실제 TCP·IOCP·콘텐츠 실행 경로를 측정한다.
로그인·매칭·로딩 이후 로비 이동/정지와 게임 다중 매치의 이동/정지를 사용한다.
기준 commit은 `199c1ab6474c0ebbfb10c9710ebba6ebfacad71a`이며 미커밋 소스·바이너리의 식별값을 별도로 저장한다.
JobQueue 자료구조·Five/Snapshot 정책·worker 수·로비의 즉시 자기 재등록은 최적화하지 않았다.
이번 변경은 관측과 측정용 입장 설정이다. [큐 단위 측정](JOBQUEUE_BASELINE.md)의 jobs/s를 실제 서버 TPS로 환산하지 않는다.

## 실행과 조회

```powershell
./scripts/Measure-ServerPerformance.ps1 -Clients 4,16,64 -Repeats 5
# 동일 부하의 계측 끔 CPU 대조. 작업/패킷/tick 계측은 수집하지 않음
./scripts/Measure-ServerPerformance.ps1 -Clients 4,16,64 -Repeats 5 -SkipBuild -DisableMetrics
```

기본 빌드는 `NewWod.Servers.slnf`의 Release x64다. `-Python`, `-OutputDirectory`, `-SkipBuild`를 지원한다.
각 실행마다 두 서버와 monitor를 재시작한다. 외부 참가자가 섞이지 않은 전용 `LOCAL_TEST`·DB 없는 실행이다.
기존 서버 실행 기록이나 출력 디렉터리가 있으면 덮어쓰지 않는다. 8910/8911/8790을 사용한다.
종료 코드 1은 기능·수집·종료 판정 중 실패가 포함됐다는 뜻이며 원시 결과는 보존한다.
반복 실행기는 준비를 포함해 시나리오당 180초 watchdog을 둔다. 이번 4/16/64명 측정은 그 안에서 끝났으며 더 큰 인원을 준비할 때는 입장 용량과 별도로 이 실행 시간 제한도 검토한다.
서버를 정리하지 못해 실행 기록이 남으면 후속 실행을 중단한다.
종료 판정의 `pending=0 sockets=0 leased=0`은 I/O·소켓·풀 자원 회수다. 모든 게임 작업을 실행 완료했다는 뜻은 아니며, 측정 끝의 미실행 작업은 별도 지표로 남긴다.

웹에서 개별 시나리오를 실행할 수도 있다.

```powershell
./scripts/Start-ServerLab.ps1 -Configuration Release -UncapAdmission
# perf-lobby / perf-match를 선택하고 더미 수와 seed 지정
./scripts/Stop-ServerLab.ps1
```

## 제한 해제 범위

`-UncapAdmission`은 자식 서버에 `WOD_PERF_UNCAPPED=1`을 전달한다. `LOCAL_TEST`에서 로비 채널당 4명 제한을 기존 전체 저장 용량인 3,000명까지 해제하고 한 채널에 수용한다.
채널 컨테이너와 전송 ID의 modulo도 같은 용량을 사용한다. 환경 설정은 실행 스크립트 종료 시 복원하며 영구 환경 변수로 저장하지 않는다.
기본 실행의 채널 용량은 기존 4명이다. 서버 snapshot의 로비 `admission.channel_capacity/storage_capacity`에 실제 설정을 기록한다.
더미 CLI/API/화면의 32명 상한도 제거했다. 양의 정수와 match의 4배수 조건은 검사한다.

게임 매치당 4명은 게임 규칙과 wire 계약이므로 유지한다. 게임은 기존 250매치/1,000명 저장 용량, 로비는 3,000명 저장 용량의 범위 검사를 유지한다.
배열 범위를 넘겨 처리하는 방식의 무제한 실행은 하지 않는다. 저장 용량 확장 자체는 구조 변경이 필요하며 이번 측정 인원은 이 용량보다 작다.
확장된 로비 ID는 Server Lab 더미가 처리한다. 기존 GUI 클라이언트는 4명 전제를 가질 수 있으므로 측정 서버의 참가자로 사용하지 않았다.
로비 채널 용량 변경은 view 목록 순회 비용에도 영향을 준다. 이 결과는 제한을 해제한 조건의 기준이며 기본 4명 채널 조건과 섞어 비교하지 않는다.

## 부하와 구간

`perf-lobby`·`perf-match`의 `performance` 객체는 `warmup_s=5`, `duration_s=20`, `interval_s=0.25`다.
기존 일반 `actions`와 함께 사용하지 않으며, 내부 고정 부하가 이동/정지와 최종 검증을 실행한다.
전체 로비 로그인 또는 4인씩 실제 매칭·직업/스킬 선택·READY·로딩 완료 후 동시 부하를 시작한다.
4인 매치 준비는 순차적이므로 동시 로그인 폭주를 측정한 결과가 아니다.
앞서 준비한 매치는 뒤의 매치를 준비하는 동안에도 tick과 NPC 일정이 진행된다. 따라서 64명 조건에는 오래된 매치의 미니언 부하도 포함되며, 모든 매치의 게임 경과 시간·NPC 수를 같게 맞춘 비교는 아니다.
매 더미가 250ms마다 이동과 정지를 번갈아 보내며, 이동 차례마다 정반대 방향을 사용해 한쪽 벽에 도달한 뒤 정지하는 부하를 피한다.
요청률은 더미당 4 packets/s, 측정 구간 80개 요청이다. 서버 응답을 기다려 다음 요청을 발행하지 않는다.
4·16·64명 조건의 동작 기준을 비교하는 측정이며, 요청률을 계속 올려 최대 TPS나 안정 수용 상한을 탐색한 결과는 아니다.
seed는 더미의 초기 방향과 반복 입력을 고정하며 스레드 실행 순서·ASLR·서버 시간·서버 NPC 난수까지 고정하지 않는다.

모든 더미의 측정 구간 이동 응답·유한한 위치 변화와 최종 정지를 검사한다.
로비 정지는 기존 명시적 ACK가 없어 0.4초 동안 자신의 이동 응답이 없음을 관찰한다. 서버 내부 정지 상태의 직접 검사는 아니다.
실패한 더미도 확인하고 실패 수를 남기며, 성능 수집 구간을 조기 통과로 바꾸지 않는다.
기존 NPC·미니언·주기 이벤트는 계속 실행된다. 근접 전투·피해·승패·NPC 애니메이션 완료 ACK를 재현한 전투 부하는 아니다.

`setup → warmup → measure → verify → cleanup`의 시각을 결과에 남긴다.
성능은 measure 안쪽의 실제 reporter snapshot 두 끝의 누적 값 차분을 사용한다. 약 18~19초의 유효 표본 구간을 실행별로 기록하며 준비/워밍업/정리 비용을 섞지 않는다.
reporter/monitor는 1초 간격이고 누락·stale·instance 변경·표본 부족을 오류로 기록한다.
매 실행의 CPU·처리량·p99를 요약한 중앙값/범위는 실행 간 비교이며 전체 실행을 합친 percentile이 아니다.

## 지표 계약

| 지표 | 출처·의미 |
|---|---|
| jobs/s | 실제 Core `jobs_completed` 차분. 로비 자기 재등록 작업을 포함하므로 유용한 요청 처리량과 다름 |
| packets/s | 서버 `CPacketMgr`의 인식된 handler가 반환한 횟수. 네트워크 recv 수/게임 플레이 TPS와 다름 |
| 이동·정지 요청 수 | 실제 `MovePacket`이 방향을 설정한 횟수. 발행 수와 구분 |
| `job_wait_us` | Core push 시각→callback 시작. 실행된 작업만 포함, allocation 전 시간은 제외 |
| `packet_job_wait_us` | 패킷 작업 생성 시도→callback 시작. 자기 재등록 작업과 분리, 세대 검사를 통과하지 못한 callback도 시작 대기에 포함 |
| `pending_packets.count/oldest_wait_us` | 아직 callback이 시작되지 않은 패킷 작업 수·현재 가장 오래 기다린 시간. 기아를 실행 완료 분포로 숨기지 않음 |
| `pending_packets.discarded` | callback 시작 전 해제된 패킷 작업 수. Clear/종료·push 실패 등의 폐기 포함 |
| 게임 `tick_delay_us` | 예약 이벤트의 목표 시각→IOCP `MatchUpdate` 진입. timer 확인·post·IOCP 대기를 모두 포함 |
| 게임 `tick_duration_us` | 실제 `MatchUpdate` 실행 구간. 목표 간격은 기존 15ms |
| 로비 `lobby_movement_gap_us` | 기존 `Move()`의 실제 위치 계산 사이 경과 시간 |
| 로비 `tick_delay_us` | 위 간격에서 기존 1ms 실행 조건을 뺀 값. 고정 주기 tick의 deadline 초과와 구분 |
| CPU % | 프로세스 CPU 누적 시간/실제 표본 구간/논리 CPU 12개. core %는 한 코어=100% |
| observer CPU·발행 lag | 더미+monitor 프로세스 CPU와 예정 발행 시각 초과. 생성기/관측 경합을 서버 한계와 구분 |

누적 histogram은 33 buckets(0, ≤1, ≤2, ≤4 … ≤2^30µs, 초과)이며 p50/p95/p99는 해당 bucket의 상한 근사다.
마지막 bucket에 percentile이 들어가면 수치를 null로 두고 overflow 수를 보고한다. 표본이 없을 때도 null이다.
로비의 최초 `Move()`는 기존 `m_updateTime`의 초기값 때문에 매우 큰 간격을 기록할 수 있다. 프로세스 전체 누적 histogram에는 이 overflow가 남지만 아래 기준값은 워밍업 이후 차분만 사용한다. 첫 이동의 초기 시간 처리도 후속 개선 대상이다.
sum/최대·bucket의 동시 snapshot은 근사값이다. 운영 중 초기화하지 않고 프로세스 재시작으로 초기화한다.
일반 작업의 대기는 실행된 작업만 기록하므로 미실행 패킷의 현재 대기와 실패 assertion을 반드시 함께 본다.
동일 `JobRef`를 동시에 여러 번 enqueue하면 일반 대기의 시각은 마지막 push 기준이 된다. 현재 서버의 런타임 작업은 enqueue마다 새 객체를 만든다.
게임 deadline과 로비 이동 간격은 기존 system clock 경로를 관측한다. 시스템 시간 변경은 통제하지 않았으며 음수 게임 초과는 0으로 처리한다.
지연 측정은 서버 내부 시각이고 네트워크 RTT가 아니다.
패킷 handler 반환 수와 더미의 실제 위치 변화 판정도 구분한다. 요청별 sequence/ACK 계약이 없어 모든 이동 명령의 개별 완료·종단 간 지연을 측정한 것은 아니다.

계측은 기존 `WOD_METRICS_DIRECTORY` 선택 활성화 경계를 사용한다. 새 histogram·시각/atomic·패킷 추적의 비용이 포함되므로 개선 전후 동일 계측으로 비교한다.
패킷 추적은 패킷 작업에만 적용하며 고빈도 자기 재등록 작업에 pending map을 만들지 않는다.
계측 끔 대조의 CPU는 실행 기록 PID·생성 시각이 일치하는 프로세스의 Windows `GetProcessTimes`로 읽는다. 없는 작업/tick 지표는 0으로 대체하지 않는다.
observer CPU는 더미·월드 관측·HTTP·수집을 합친 비용이다. 전체 PC의 다른 프로세스·온도·affinity는 통제하지 않는다.
이 PC에서 게임 IOCP worker는 기존 `hardware_concurrency()/2`에 따라 6개, 로비 IOCP worker는 4개이고 로비 JobScheduler 소비자는 1개다. 전체 CPU 50%라도 게임 IOCP의 6개 코어가 포화된 상태일 수 있다.
계측 끔은 기존 reporter·월드 snapshot과 새 작업 계측을 함께 끈다. 따라서 CPU 차이는 전체 관측 경로의 대조이며 새 histogram만의 비용은 아니다.
특히 기아가 발생하는 로비는 실행마다 유용한 처리량도 달라질 수 있어 CPU 차이만으로 계측 비용의 비율을 확정하지 않는다.
현재 큐가 shared_ptr 주소로 우선순위를 정하므로 패킷 추적 객체의 추가 할당도 실행 순서에 영향을 줄 수 있다. 계측 켬/끔에서 완료 대상이 같다는 전제를 두지 않고, 개선 전후에는 같은 계측을 유지한다.

## 측정 결과와 검증

환경은 Ryzen 5 7500F(6코어/12논리 CPU), RAM 33,933,996,032 bytes, Windows 11 Home 10.0.26200, 균형 조정 전원 계획이다.
Visual Studio 2026/v145(14.51.36231, cl 19.51.36260.0), Release x64 `LOCAL_TEST`, Python 3.12.14를 사용했다.
계측 켬 결과는 `artifacts/logs/server-baseline/20261011-final-on`에 보존했다.

게임 시나리오 동안 로비 서버는 입력이 없어도 약 한 코어의 CPU를 사용했다. `idle.json`에서도 확인되며 기존 `TimerFunc`의 빈 큐 `yield()` 반복은 별도 개선 후보다.

다음은 실행별 p99 bucket 상한과 미실행 대기의 중앙값이다. 일반 작업 p99만 보면 로비의 높은 빈도 자기 재등록에 패킷 기아가 가려진다.

로비 tick 지연은 1ms 이동 실행 조건 초과이고 게임은 예약 deadline 초과다. 로비의 tick 실행 시간은 이 경로에 추가하지 않아 null로 남는다.
로비의 패킷 p99 bucket 상한 33.554초를 실제 정확한 33.554초 대기라고 해석하지 않는다. 미실행 최장 대기는 별도로 관측한 실제 경과 시간이다.
로비 64명의 끝 미실행 패킷은 5,519~6,083개, 관측된 최장 미실행 대기의 전체 최대는 24.425초였다.
게임 64명의 tick 지연 p99 상한은 실행별 131.072~262.144ms였다.
게임 tick 평균 실행 시간의 반복 중앙값은 4/16/64명에서 22.630/25.828/39.556ms이며, 매치당 tick 처리율은 39.81/36.46/9.44회/s였다.
현재 15ms 목표 간격과 비교해 이미 실행 비용이 크며, 패킷 큐의 처리량만으로 콘텐츠 tick 비용을 설명하지 않는다.

로비 4명은 매번 3명의 이동/정지 판정이 실패했다. 16명은 12~15명, 64명은 57~64명이 실패했다.
게임 64명은 측정 구간에 진입한 4회 모두 앞의 15매치 60명의 측정 중 자기 이동 응답이 없었고, 마지막 매치 4명만 이동이 관측됐다.
서버 handler 처리율이 요청률에 근접해도 실제 위치 변화가 보장되지 않는 사례다. 서버 내부 기아와 응답/전송 문제의 원인을 이 합계로 확정하지 않는다.
기존 웹 월드의 일정 연결은 첫 8그룹까지만 지원한다. 64명 실행의 성능 counter/histogram과 더미별 이동 판정은 16매치 전체를 포함하며, 서버 원본 `content.matches`에도 전체 일정이 있다. 16매치 전체의 웹 일정 연결은 후속 확장이다.
게임 16명 seed 5(client 3), 64명 seed 4(client 19)는 `match-transfer: 0 bytes read on a total of 2 expected bytes`로 준비 중 실패했다.
기능 실패와 `측정 시작/끝 구간 없음`을 모두 보존했고 성능 표의 표본에서만 제외했다. 실패를 대체하는 자동 재시도는 하지 않았다.
매치 목적지 패킷을 비동기로 보낸 직후 disconnect하는 기존 경로는 이 연결 종료의 추가 조사 후보다.

측정 구간의 더미+monitor CPU는 한 코어 기준 반복 중앙값이 로비 4/16/64명에서 4.49/8.38/28.24%, 게임에서 7.74/18.40/3.95%였다.
발행 예정 시각 초과의 최대는 로비와 게임 4/16명에서 0ms, 게임 64명에서 16ms였다. 250ms 발행 주기의 CPU 포화는 이 표본에서 관측되지 않았다.
계측 켬의 유효 측정 구간에서 양쪽 서버의 job 실패·I/O 오류 증가분은 모두 0이었다. 준비·연결 종료 과정의 누적 I/O 오류까지 0이라는 뜻은 아니다.
30회 모두 로비 채널 용량 3,000 설정으로 시작했으며 `Max user exceeded` 로그는 없었다. 측정 구간에 도달한 실행은 요청한 전체 더미의 준비를 완료했다. 준비 중 EOF의 원인은 별도로 조사한다.

계측 끔 대조는 `artifacts/logs/server-baseline/20261011-final-off`에 보존했다. 동일 30회 중 27회가 측정 구간에 도달했고 기능 판정은 9회 통과/21회 실패였다. 전체 60회에서 종료 자원 회수와 더미 연결 0을 확인했다.

계측을 꺼도 로비 15회 전체가 실패했고 게임 64명의 측정 가능한 3회 모두 60/64명의 자기 이동을 관측하지 못했다. 게임 4명은 5/5회, 16명은 준비가 완료된 4/4회 통과했다.

두 조건의 실패 재현은 계측만으로 현상을 설명할 수 없음을 보여준다. CPU의 양수/음수 차이는 전체 관측 비용·실행 순서·콘텐츠/환경 차이가 섞인 값이며 새 histogram의 정확한 비용이나 최적화 효과로 해석하지 않는다.

대조 시작 전 PowerShell의 단일 옵션 문자열 splatting을 배열로 수정했다. 서버 시작 전 CLI 인자 오류였고 계측 켬 측정에는 영향을 주지 않았다.

서버·더미·수집기·시나리오·실행 파일은 계측 켬/끔 사이 동일하다.

## 개선 후 비교 시 유지할 조건

같은 바이너리 구성·입장 설정·계측·시나리오·4/16/64명·seed 1~5·구간 길이를 사용하고 각 실행마다 서버를 재시작한다.
CPU나 jobs/s만 개선 기준으로 삼지 않는다. 더미별 이동/정지, 처리된 패킷과 요청률, 미실행 대기, tick 초과와 종료 자원도 함께 비교한다.
로비의 shared_ptr 우선순위와 즉시 자기 재등록, 게임의 6개 IOCP worker·콘텐츠 실행/전송 비용을 구분해 가설을 세운다.
게임 tick 안의 큐 처리·충돌/AI·전송을 세분화한 시간과 매치별 입력/응답·전송 대기 관측은 추가 진단 후보다. 현재 합계 지표만으로 64명 응답 실패의 원인을 확정하지 않는다.
모든 매치의 게임 나이/NPC 수를 동일하게 맞추는 시나리오나 요청률을 올리는 포화 실험을 추가하면 이 기준과 다른 조건으로 별도 기록한다.

후속 FIFO/전송 적체 수정과 동일 조건 재측정은 [개선 전후 기록](JOBQUEUE_IMPROVEMENT.md)에 있다. 이 문서의 수치와 미검증 범위는 기준 측정 당시 상태다.
