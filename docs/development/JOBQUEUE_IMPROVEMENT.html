02분석한 원인

LOBBY / 주소 우선순위

이동 작업이 정지 패킷을 굶겼습니다

작업·ready 목록이 포인터 주소로 우선순위를 정했습니다. 즉시 자기 재등록하는 높은 주소의 이동 작업이 계속 선택됐습니다.

concurrent_priority_queue<JobRef> m_jobs;
std::priority_queue<JobTarget *> m_queue;
// 포인터 주소로 우선순위가 정해짐
기존 선언 발췌 · JobQueue / JobScheduler
GAME / 직렬 전송

좌표는 변했지만 과거 상태만 도착했습니다

16개 매치 모두 입력·좌표가 갱신됐습니다. 프레임마다 완료 처리를 기다리는 전송에 약 49만 context가 쌓였습니다.

프레임 1개 전송 → 완료를 worker가 처리
                 ↓
            다음 프레임 발행
// 같은 6개 worker가 매치 tick도 실행
설명용 흐름 · 실제 구현 코드가 아님

분리 실험: FIFO만 적용하거나 TCP_NODELAY만 적용해도 게임 64명 실패는 남았습니다.

03해결 방식

LOBBY / FIFO + 대상 순환

먼저 게시한 작업과 대상부터 처리합니다

작업·ready를 FIFO로 바꾸고 예산 뒤 남은 대상을 꼬리에 넣습니다. 실행 직렬화와 Five / Snapshot 예산은 유지합니다.

std::queue<JobRef> m_jobs;
std::queue<JobTarget *> m_queue;
// 가장 먼저 게시한 대상부터 실행
target = m_queue.front();
m_queue.pop();
// 남은 작업은 ready 목록 뒤에 재등록
실제 코드 발췌 · 서로 다른 선언/처리 구간, 중간 생략
GAME / 대기 프레임 묶음 전송

이미 기다리는 프레임을 최대 64개씩 보냅니다

첫 프레임은 즉시 보냅니다. 이후 대기 프레임만 묶어 완료 대기 횟수를 줄이며 전송 순서·부분 전송·개별 회수는 유지합니다.

for (auto *queued : _state.m_sends)
{
    _state.m_sendBatch.push_back(queued);
    // 프레임 bytes를 소유 버퍼에 복사…
    if (_state.m_sendBatch.size() == 64)
        break;
}
실제 IssueSend 발췌 · 버퍼 복사 부분 생략

별도 수정: SC_MATCH 직후 Disconnect를 제거해 목적지 패킷의 전달 취소를 막았습니다. 새 연결 유지 timeout 정책은 추가하지 않았습니다.
