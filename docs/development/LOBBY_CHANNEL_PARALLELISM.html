1. 결과

밀집 채널에서는 worker4의 대기 개선이 확인되지 않았고 CPU가 증가했다. 512명에서는 정지·종료 실패를 관측했다.

실제 실패: 4채널×128명·worker4의 2번째 실행에서 120/512명 최종 정지 timeout. 송신 대기5,540,022건·private bytes 최고3.16GB, 로비 종료15초 제한 초과로 정상 종료에 실패했다. 해당 조건은3/6회만 수행하고 중단했다.

추가 밀집 측정: 4채널×32명에서 대기 p99 상한 131.1→131.1ms, CPU 8.80→14.23%였다. 밀집 실행의 송신 대기는 최고 5,540,022건이었다. 검증 성공 20/21회. 밀집 비교와 생성기 한계를 함께 확인해야 한다.

비교 범위: 기능은 원본 main@54af931c 대비 수정 전후다. 성능은 개선 코드 안에서 worker 수만 바꾼 대조이며, 원본 main의 같은 32채널 조건 성능은 미측정이다.

2. 분석한 원인

모든 채널이 로직 소비자 하나를 공유

채널이 나뉘어도 로직 실행은 한 줄이었다. IOCP 4개와 로직 worker 1개는 서로 다른 역할이다.

// 수정 전 · CServer::Run 발췌
producers.Launch([] {
    GPacketJobQueue->ProcessJob();
});

정리 순서와 제거 수신자가 잘못됨

종료 유저의 ID를 초기화한 뒤 상대 시야에서 재조회했다. 채널 이동은 관찰자의 시야를 지우면서 본인에게 패킷을 보냈다.

// 수정 전 경로 · 개념 코드
client.Reset();                 // ID = -1
observer.Remove(client.ID());   // REMOVE(-1)
observer.Delete(..., mover.Sender()); // 수신자 오류

유저별 큐의 잠금은 이웃 유저의 좌표·시야까지 보호하지 않는다. 소비자 수를 늘리기 전에 채널 소유권을 정리해야 했다.

밀집 조건에서는 전송 적체가 추가로 관측됨

입력 처리율이 목표에 근접해도 송신 대기는 누적됐다. 같은 채널은 직렬이므로 worker 증가가 채널 내부 연산을 분할하지 않는다. CPU 증가·전송 적체의 세부 원인 분해는 아직 미수행이다.
