2. 분석한 원인

실행 시간과 예약 대기를 분리했습니다. 타이머 전달 전 대기가 큰 구간과 IOCP 처리 대기가 커지는 구간을 아래 그래프로 확인할 수 있습니다. CPU 전체 비율만으로 여유가 있다고 판단할 수 없습니다.

// 현재 게임 타이머 경로 (핵심 흐름)
이벤트 pop → 아직 미래이면 다시 push → sleep_for(1ms)
기한 도착 → Post → IOCP 작업 시작 → 게임 tick
다음 tick = 현재 시각 + 15ms

로비는 IOCP 4스레드와 별개로 JobScheduler를 단 한 스레드에서 실행합니다. 이동은 자신을 재등록하며 지형 충돌·채널 전체 가시성 검사·근처 플레이어 송신을 수행합니다. 전체 CPU가 낮아도 이 처리 경로에는 대기가 쌓일 수 있습니다.

// Lobby CServer::Run / CClient::ProcessUpdate
producers.Launch([] { GPacketJobQueue->ProcessJob(); }); // 1개
Move(); // 충돌 + 채널 전체 순회 + 근처 대상 송신
if (이동 중) { PushJob(ProcessUpdate); AddSessionQueue(this); }

같은 누적 실행의 tick CPU cycle 비중입니다. 미니언 내부에 HeightRay/NavRay가 포함되므로 열을 합산하지 않습니다. JobQueue 내부 실행 비중만으로 모든 스케줄링 비용을 설명할 수는 없습니다.
