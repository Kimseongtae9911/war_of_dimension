2. 분석한 원인

확인: 최적화한 비용과 서버 병목이 다르다. 게임의 패킷 작업은 약 256개/s이고 이동·NPC·송신은 tick에서 실행한다. callback 시간은 전체 tick 합산 시간의 최대 0.0017%였다. 큐 잠금 비용을 포함하지 않으므로 큐 비용 전체의 비율로 해석할 수 없다.

유력: 논리적 큐 분리가 메모리 경합까지 없애지는 않는다. 인접한 게시/실행 큐·잠금·공유 카운터를 64바이트 단위로 분리한 진단 버전은 1생산자·1소비자 계측 끔 비용이 143.14→122.08ns/job(-14.7%)로 줄었다. atomic·순서·알고리즘은 유지했다. 캐시 배치 비용을 뒷받침하지만 특정 멤버의 false sharing은 하드웨어 카운터로 확정하지 않았다.

미입증: atomic 증가가 악화 원인이라는 가설. 로비의 ProcessUpdate가 하나를 처리하고 하나를 다시 넣으면 일괄 처리 이득이 줄고 atomic 증감 2회가 추가된다. 그러나 단일 스레드 비용 대조에서는 계측 켬/끔에 따라 방향이 달랐고 범위도 겹쳤다. 추가 연산이 있다는 사실만으로 전체 비용 증가를 단정할 수 없다.

// 실제 구현의 핵심 · 계측/예산 생략
PushJob: m_jobs.push(job); ++m_queued;
ProcessJob:
  if (m_readyJobs.empty()) {
    lock(m_mutex); m_readyJobs.swap(m_jobs);
  }
  m_readyJobs.pop(); --m_queued;
  job.Execute(); // 로비 이동은 여기서 다시 PushJob

이전 CPU 감소는 처리량 감소를 동반했다. 원본 추가 진단에서도 tick p99 상한 262.144ms와 낮은 갱신량이 나타났다. 과거 실행에는 시스템 부하/CPU 성능 비율이 없어 편차의 정확한 원인은 미확정이다.

3. 해결 방식

이번에 적용: 판정을 교차 실행·실제 갱신량·평균 지연 중심으로 보완했다. 후속 제안: 실제 서버 개선으로의 채택을 보류하고 tick 지배 비용부터 분해한다. 추가 구현과 원복은 이번 조사에서 수행하지 않았다.

// 검증 기준 · 의사 코드
for (같은 seed의 before/after 교차 실행) {
  비교(CPU, 실제 tick 수, 이동 수, 작업 대기, 실패율);
}
비용_분리(1개 처리, 4개 묶음, 자기 재등록);
// atomic 제거 대조군은 단일 스레드 진단 전용

측정 도구 흐름도 · atomic 제거를 제품 코드의 해결책으로 적용하지 않는다. FIFO·Five/Snapshot·실행 직렬성·lost wakeup 계약을 보존하는 후속 설계가 필요하다.
