DSN 등록과 소스 매크로 수정을 없애고, 모든 DB 작업을 전용 FIFO로 이동했다. DB 결과를 적용한 뒤 같은 세션의 다음 요청을 실행한다.

전체 DB 작업 완료 시간은 약 125ms로 유지됐다. 단일 DB worker의 처리량 한계, 같은 계정의 복수 로그인 동기화, 운영 DB·블록체인·GUI 플레이 검증은 남아 있다.

02 원인

별도 DB 스레드가 있어도 로비 전체가 기다렸다

로그인·조회는 패킷 처리 중 ODBC를 직접 호출했다. 쓰기 worker도 SQL 실행 동안 LockGlobal()을 잡았고, 조회와 쓰기는 같은 연결에 다른 경로로 접근했다. 이벤트 시각만 비교하는 priority queue에는 동일 시각의 안정된 순서 계약이 없었다.

이전 코드의 핵심 경계

// 이전 경계: CDataBaseThread::ThreadFunction
auto global = GLobbyDispatcher->LockGlobal();
m_dataBase->SavePlayerInfo(ev.m_id, ev.m_playerInfo);
// 조회는 Packet handler가 GetDataBase()로 직접 실행
// 쓰기는 wakeUpTime 기반 priority queue 사용

실패가 생기는 예

연속 구매 뒤 조회가 이전 쓰기를 기다리지 않거나, 느린 SQL이 채널 전체의 작업을 막을 수 있었다. 종료 시 전체 PlayerInfo snapshot을 저장하면 DB에서 확정된 최신 잔액도 오래된 값으로 덮어쓸 수 있었다.

코드 근거: CDataBaseThread / CPacketMgr / CClient. 이전 상태는 현재 브랜치의 기반 커밋에서 추출했다.

03 해결

SQL 실행·세션 순서·결과 적용의 책임을 분리했다

// 현재 경계: CClient::RunDatabase
GLobbyDispatcher->Suspend(m_workQueue);
database->Submit([snapshot](CDataBase& db) {
    auto result = query(db);     // 로비 잠금 밖 SQL
    ResumeWithGeneration(result); // 세션 맨 앞에서 완료 적용
});

위 코드는 실행 경계를 요약한 의사 코드다. 실제 함수는 CClient::RunDatabase, LobbyDispatcher::Suspend/Resume, CDataBaseThread::Submit이다.

유지하는 계약

전용 worker가 ODBC 연결을 단독 소유한다. mutex 아래 수락된 순서대로 실행하며, 요청 값은 복사하고 완료는 세션 큐 맨 앞에서 generation을 확인한다. 현재 작업보다 빨리 완료가 도착하는 경합도 검사했다.

상한 4096건, 조건변수 대기, 종료 시 수락 작업 drain. 구매는 트랜잭션 확정 뒤 성공 응답을 보내며 실패는 rollback 후 연결을 종료한다. SQL 로그인·질의 timeout은 각각 5초다.

확대 가능한 실행 구조도 · 잠금·큐·소유권을 선택한 이유와 비용

처음 한 번 LocalDB·ODBC x64 설치가 필요하다. 스크립트는 전용 로컬 스키마와 저장 프로시저 16개를 준비하고 .runtime에 연결 설정을 저장한다. 기본 실행은 계속 DB disabled이며, 환경변수 WOD_DB_CONNECTION / WOD_DB_CONFIG로 별도 연결을 지정할 수 있다. 운영 스키마의 자동 마이그레이션은 수행하지 않는다.
