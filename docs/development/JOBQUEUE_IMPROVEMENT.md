## 확인한 원인과 분리 실험

로비에는 두 단계의 기아가 있었다. `JobQueue`의 PPL `concurrent_priority_queue<shared_ptr<IJob>>`는 Job의 시각 비교가 아니라 shared_ptr 주소를 비교했다.
`JobScheduler`의 `priority_queue<JobTarget*>`도 대상 주소를 비교했다. 이동 작업은 방향이 0이 아니면 즉시 자기 작업을 재등록하므로,
높은 주소의 작업/대상이 계속 선택되면서 먼저 도착한 정지 패킷이나 다른 대상이 실행되지 않았다.
할당 주소 순서대로 12개 작업을 게시하는 회귀를 기존 구현에 실행해 FIFO 순서 검사가 실패하는 것을 확인했다.
높은 주소의 자기 재등록 작업과 낮은 주소의 패킷/대상도 별도로 검사했다. 기존 단위 기준의 hot 200,000개 선행 실행 10/10회는 같은 문제의 다른 재현이다.

게임 64명은 4명씩 16개 매치다. 진단 로그에서는 16개 매치 모두 이동 입력 404개(방향 nonzero 200개)를 처리하고 서버 좌표도 변했다.
첫 60명에게는 과거 정지 좌표 패킷만 도착하고 마지막 매치 4명만 측정 중 이동을 받았다. 입력 누락과 서버 좌표 미갱신으로 설명할 수 없었다.
Core는 연결별로 프레임 하나의 native 완료를 IOCP worker가 처리한 뒤 다음 프레임을 발행했다.
동일한 6개 worker가 비용이 큰 매치 갱신도 수행해 이 직렬 전송 경로가 갱신/NPC 출력량을 따라가지 못했다.
진단 실행에서 pending I/O와 풀 대여가 약 49만 개까지 늘었고, FIFO만 적용해도 전송 대기는 다시 증가했다.

| 분리 실험 | 변경 | 게임 64명 결과 |
|---|---|---|
| `diagnostic-before` | 기존 구현 + 한시적인 입력/좌표 로그 | 16개 매치 입력 처리·좌표 변화 확인, 60명 이동 미관측 |
| `isolate-lobby` | 로비 FIFO·매치 목적지 전달 수정, 게임 기준 바이너리 유지 | 64명 준비 완료, 60명 이동 미관측 |
| `isolate-nodelay` | 게임 기존 큐 + TCP_NODELAY | 60명 이동 미관측, private bytes 약 295 MB |
| `isolate-fifo` | 로비/게임 FIFO, 기존 단일 프레임 전송 | 전송 대기 누적, 이동 검증 실패 |
| `isolate-batch` | FIFO + 대기 프레임 묶음 전송 | 64명 모두 이동/최종 정지 통과, 종료 자원 0 |

TCP_NODELAY 단독 실험은 개선되지 않아 변경에서 제외했다. 기존 게임의 중복 이동 broadcast·NPC 동작·worker 수·tick 예약 간격은 유지했다.
진단 디렉터리는 `artifacts/logs/jobqueue-improvement/`이며 실패/준비 EOF를 포함한 모든 실행을 보존했다.
일부 초반 진단 metadata의 optimized=false는 당시 도구 기본값이다. 위 표와 디렉터리명이 실험 변경을 구분하며, 최종 실행에는 명시적인 stage=after를 기록한다.

매치 준비 중 EOF는 별도 문제였다. 로비가 `SC_MATCH`를 Send한 직후 Disconnect를 호출해 Core의 CancelIoEx/대기 전송 취소 경로로 들어갔다.
목적지 패킷 전달보다 취소가 먼저 완료될 수 있었다. 즉시 Disconnect를 제거하고 목적지를 수신한 클라이언트의 기존 연결 종료를 받도록 했다.
실제 GUI 클라이언트와 더미 모두 SC_MATCH 수신 뒤 로비 연결을 닫는다. 전달 성공 뒤 기존 EOF/사용자 정리 경로가 동작한다.
이 수정은 새로운 인증/접속 유지 timeout 정책을 구현한 것은 아니다.

## 적용한 계약

`JobQueue(JobBudget)`의 두 정책을 유지하며 작업 저장소를 mutex로 보호하는 FIFO `std::queue`로 바꿨다.
게시 순서는 큐 mutex에서 게시가 확정된 순서다. 서로 다른 생산자의 호출 시작 시각 순서나 예약 시각 실행은 보장하지 않는다.
Five는 한 번에 최대 5개, Snapshot은 실행 시작에 확인한 개수만 처리한다. callback은 게시 mutex 밖에서 실행하고 기존 실행 mutex로 직렬화한다.
callback에서 자기 재등록이 가능하며 먼저 게시된 작업을 앞지르지 않는다. 예외 뒤 나머지 작업은 큐에 남고, Clear는 실행과 직렬화해 분리한 작업을 폐기한다.
ready 대상도 FIFO로 바꾸어 예산 뒤 남은 대상을 꼬리에 넣는다. 중복 등록 방지·조건 변수 깨우기·disconnect 정리·Stop 계약은 유지한다.
Resource의 풀에는 여전히 PPL priority queue가 필요해 해당 include를 `Resource.h`에 명시했다.

전송은 이미 기다리는 프레임을 최대 64개(프레임당 최대 256 bytes) 모아 연결별 소유 버퍼에 복사한다.
첫 프레임은 즉시 발행하며 묶음을 채우려고 기다리지 않는다. 프레임 순서·내용·wire layout·출력 빈도는 바꾸지 않는다.
부분 전송은 같은 배치의 미전송 bytes부터 이어서 보내며 후속 배치가 앞지르지 않는다.
native OVERLAPPED는 배치 첫 context가 소유하고 완료/실패 뒤 각 원래 context를 개별 완료 처리한다.
나머지 context는 완료 통지를 게시할 때까지 pending 상태를 유지하며 연결 callback 직렬화·generation/풀 회수·종료 배출을 따른다.
Disconnect/Close는 active 배치 전체를 native 완료까지 유지하고 아직 발행하지 않은 프레임만 개별 취소한다.
연결별 배치 버퍼는 재사용하지만 전체 전송 대기량에 hard limit/backpressure를 새로 추가하지 않았다.

## 추가한 관측과 재현

`GET /api/state`와 결과의 서버 snapshot에 `send_queue`를 추가했다. 기존 schema_version=1의 선택 필드다.

| 필드 | 단위·의미 |
|---|---|
| `count` | 연결들의 active/대기 전송 context 수 합계. native 완료 뒤 개별 통지 대기 중인 context는 제외 |
| `max_socket_count` | 한 연결에서 가장 많은 active/대기 context 수 |
| `native_calls` | 프로세스 누적 WSASend 발행 시도 수. 부분 전송 재발행·즉시 실패 포함 |
| `batches` | 프로세스 누적 새 배치 발행 수 |
| `frames` | 새 배치에 포함한 원래 프레임 수 합계. 성공 전달 수와 구분 |

이 값은 기존 IocpService 상태 mutex 아래에서 읽는다. snapshot은 기존 1초 주기이며 프로세스 재시작 때 초기화된다.
monitor는 필드를 보존하고 화면에 전송 대기/연결별 최대 대기를 표시한다. 통계 도구는 측정 구간의 peak/end와 native 호출·배치·프레임 증분/s를 계산한다.
기존 결과에 필드가 없으면 0으로 채우지 않고 생략한다. pending_io의 peak/end도 원래 snapshot에서 요약한다.
Peer의 수신 예외는 port·phase·시각·closing 여부와 함께 API/결과에 남기고 재접속 때 현재 error를 지운다.
정상 연결 종료의 EOF 기록과 측정 중 오류를 구분한다. 성능 판정은 현재 Peer.error도 확인하며 이동/최종 정지의 기존 조건과 10초 timeout을 완화하지 않는다.

```powershell
scripts/Measure-ServerPerformance.ps1 -Stage after -SkipBuild -OutputDirectory artifacts/logs/jobqueue-improvement/final-on
scripts/Measure-ServerPerformance.ps1 -Stage after -SkipBuild -DisableMetrics -OutputDirectory artifacts/logs/jobqueue-improvement/final-off
scripts/Measure-JobQueue.ps1 -OutputDirectory artifacts/logs/jobqueue-improvement/micro-final
```

전후 모두 4/16/64명·perf-lobby/perf-match·seed 1~5, 5초 워밍업/20초 측정/250ms 발행, 매회 서버 재시작과 입장 소프트 제한 해제를 적용한다.
4인 매치 규칙·저장 용량 guard는 유지한다. 서버는 Release x64 LOCAL_TEST이고 기기·전원 계획·콘텐츠 데이터도 같은 조건이다.
목표 입력은 1인당 4개/s로 16/64/256 packets/s다. 최대 처리량/수용 상한 측정으로 해석하지 않는다.
준비 중 먼저 시작한 매치의 나이와 NPC 수 차이는 기존 기준에도 존재하고 그대로 유지한다.

## 검증과 남은 범위

Debug/Release 서버 빌드, Core 199검사와 Protocol ABI 110종/106상수, 두 구성의 실제 네트워크 12종·보스4/5 매칭·초기화 실패4종을 통과했다.
Core에는 FIFO/자기 재등록/ready 순환/예외 뒤 잔여 실행/동시 생산·소비 직렬 실행과 배치 부분 전송/오류/취소/개별 회수를 추가했다.
Python 29검사와 실제 Server Lab API 7종·telemetry export 실패 격리·종료 자원 0을 통과했다. 에이전트 환경 정적 검사도 227소스로 통과했다.
최종 UTF-8 56파일·Python AST8·프로젝트 XML2·문서 링크114·JS2·PowerShell4·git diff --check를 통과했다.
1265px 브라우저에서 양쪽 전송 대기/연결별 최대 대기 표시, 가로 overflow 0·console 오류/경고 0을 확인했다. 검증용 서버·monitor·임시 탭은 종료했다.
Archify showcase 9/9·composition 오류/경고 0·4크기 containment와 light/dark PNG 직접 점검·JSON/HTML hash 대조를 통과했다.
서버의 기존 경고(C4065·C4101·C4244·C4305·C4309)는 별도로 유지하며 경고를 숨겨 성공 처리하지 않았다.

기아 해소 뒤에도 로비 64명의 대기와 게임 16/64명의 tick 비용은 남을 수 있다.
로비의 tick_delay는 실제 이동 계산 간격에서 1ms를 뺀 관측이며 정지 시간도 포함한다. FIFO 적용 뒤 그동안 굶던 대상의 갱신도 실행하므로
기존의 소수 hot 대상만 반영한 낮은 값과 단순히 빠름/느림으로 비교하지 않는다. 게임 tick의 목표 15ms 초과와 구분한다.
로비 jobs/s의 감소도 빠른 자기 재등록 반복이 줄고 실제 패킷/다른 대상이 실행된 결과일 수 있어 요청 처리량·기능 결과와 함께 해석한다.
후속으로 로비의 재등록 주기/중복 갱신 체인 여부·단일 content worker·view/지형 조회, 게임의 AI/충돌/전송 실행 구간을 세분화해 측정한다.
로비 TimerFunc의 빈 큐 yield 반복도 소스에서 확인했으므로 thread별 CPU 측정과 분리한다. 이번에 thread별 CPU 비용까지 확정한 것은 아니다.
전체 대기량 제한/backpressure·장시간 안정성·포화 요청률·모든 매치의 나이/NPC 수 동기화는 별도 과제다.
이번 결과는 LOCAL_TEST 고정 부하의 이동/정지 관측이며 전체 전투·승패·GUI 플레이·운영 DB/블록체인 검증을 의미하지 않는다.
로비 최종 정지는 기존과 같은 0.4초 무응답 관찰로 서버 내부 정지 상태의 직접 ACK가 아니다.

## 후속 커밋 분리와 HTML 보고서 검증

텔리메트리·측정 도구·기준 문서를 선행 커밋 대상으로 분리하고 FIFO·전송 배치·매치 전달 수정·해당 회귀와 이 보고서는 개선 작업으로 남겼다.
분리한 계측 snapshot만 적용해 Release Core164/ABI·서버 빌드를 통과했고, 전체 개선 소스 bytes 복원 뒤 Core199/ABI·서버 Release 빌드와 Python29를 다시 통과했다.
이 검사는 커밋 분리의 독립 빌드와 복원을 확인한 것이며 성능120회를 다시 실행한 것은 아니다. 실제 측정 당시 metadata/hash와 원시 결과는 별도 보존한다.
