# JobQueue 기준 측정과 개선 방향

2026-10-11에 `codex/jobqueue-optimization` 브랜치를 생성하고 현재 Core 큐의 단위 처리량을 측정했다.
기준 commit은 `199c1ab6474c0ebbfb10c9710ebba6ebfacad71a`다. 운영 `Concurrency.h`·`Metrics.h`는 변경하지 않았다.
이번 범위는 현재 처리량과 병목 후보 확인이며, 최적화 구현·개선 후 비교·서버 전체 TPS 측정은 후속 작업이다.
[검사 지침](../guides/SERVER_PERFORMANCE.md), [Core 계약](../architecture/SERVER_CORE.md), [측정 구조도](../diagrams/jobqueue-baseline/README.md)를 함께 참조한다.
이 문서의 hash·수치는 실제 서버 계측 확장 전의 최초 단위 측정 시점이다. 이후 [실제 서버 기준 측정](SERVER_BASELINE.md)에서 작업 대기/tick 계측을 추가했으므로 현재 파일 hash와 구분한다.
새 계측을 켠 단위 측정은 기존 수치와 그대로 전후 비교하지 않고 동일 계측으로 기준을 다시 확보한다.

## 재현과 결과 조회

```powershell
./scripts/Measure-JobQueue.ps1 -Jobs 1000000 -Repeats 5
```

스크립트는 `ServerCore.Tests`를 x64 Release로 빌드하고 실제 `JobQueue`·`JobScheduler`를 사용하는 `--jobqueue-benchmark` 모드를 실행한다.
테스트 프로젝트 전체의 Release 최적화를 `/O2`로 명시했다. 서버 프로젝트의 빌드 옵션은 바꾸지 않았다.
기본 실행은 작업 200,000개·반복 5회다. 위 명령은 최종 기준 측정에 사용한 작업 1,000,000개 조건이다.
`-OutputDirectory`, `-Python`, `-Jobs`, `-Repeats`를 지정할 수 있으며 기존 결과 디렉터리는 덮어쓰지 않는다.

결과는 Git 제외 `artifacts/logs/jobqueue-baseline/<실행 시각>/`에 저장한다. 에이전트는 다음 파일을 직접 조회할 수 있다.

| 파일 | 내용 |
|---|---|

| `metadata.json` | commit/브랜치·tracked diff·큐/도구/바이너리 SHA-256·입력·워밍업·샘플링 조건 |

성능 도구는 단일 큐/여러 큐를 최대 속도로 채우고 비운다. 실제 서버 패킷 도착 주기와 다르므로 jobs/s를 접속자 수·TPS로 환산하지 않는다.
실행 프로세스별 45초 제한과 실패 기록을 두고, 실패 실행을 요약에서 조용히 제외하지 않는다.

## 측정 조건과 판정

7가지 처리량 부하에 Five/Snapshot·JobMetrics 끔/켬을 조합하고, 상세 지연 4조건·공정성 2조건·idle 1조건을 추가했다.
총 35조건을 각각 5회 실행한다. 처리량 부하는 같은 프로세스에서 20,000개 작업을 워밍업한 뒤 실제 구간을 측정한다.
실행 순서는 seed `20261011`로 섞는다. callback은 큐별 완료 수와 ID 합계를 갱신하며 큐별 카운터를 64 bytes로 분리해 측정 도구 자체의 공유 카운터 경합을 줄였다.
성공은 처리량 기준 통과가 아니라 전체 작업 수·ID 합계·잔여 작업·활성 계측 카운터의 일치다.
상세 모드에서는 모든 작업의 atomic 실행 횟수로 누락/중복을 추가 검사하고, 67개마다 enqueue 시도→실행 시작/완료 시각을 기록한다.
67은 4 생산자·32 큐와 공약수가 없어 특정 생산자/큐에 표본이 편중되지 않도록 선택했다.

| 부하 | 구성·측정 범위 |
|---|---|
| `single` | 생산자 1·실행자 1·큐 1, 실행 중 생성/할당·전송·회수 포함 |
| `producers4` | 생산자 4·실행자 1·큐 1, enqueue 경합 |
| `consumers4` | 생산자 4·실행자 4·큐 1, 같은 실행 mutex 경합 |
| `queues32` | 생산자 4·실행자 4·큐 32, 큐를 실행자별로 분할. 실제 ready 스케줄러를 통하지 않음 |
| `burst` | 작업 전부를 미리 enqueue한 큐를 실행자 1명이 비움. preload 시간 별도, jobs/s는 drain만 |
| `preallocated` | 작업/소유 참조를 사전 생성·보유. 측정 중 새 할당/최종 해제 제외, working set은 달라짐 |
| `mixed` | 32 큐에서 997개마다 한 callback이 50µs busy wait. 나머지는 기본 callback |
| `fairness` | 실제 Scheduler의 높은 주소 대상이 자기 작업을 재등록하는 동안 낮은 주소 대상의 1개 작업 대기 관찰 |
| `idle` | 빈 실제 Scheduler가 condition variable에서 1초 차단 대기할 때 프로세스 CPU 시간 |

스레드 생성·사전 할당·burst backlog 준비는 처리량 측정에서 제외하며, barrier 해제 직전부터 모든 worker join까지 측정한다.
생산자 완료 전 consumer는 `ProcessJob()`을 반복 호출한다. 이 polling 부하는 단위 측정 전용이며 서버의 깨우기/실행 경로와 구분한다.
`fairness` 대기 시간은 준비된 두 대상을 worker에 공개한 시점부터 probe callback까지다. hot 작업이 전부 완료될 때까지 실행하고 조기 probe도 기록할 수 있다.
상세 지연은 allocation/큐 대기와 callback 완료를 포함하며 네트워크 RTT가 아니다. 실행별 percentile의 중앙값을 전체 표본의 percentile로 해석하지 않는다.

## 현재 실행 의미

`JobQueue`는 PPL `concurrent_priority_queue<shared_ptr<IJob>>`를 사용한다. `Job::operator<`의 시간 비교가 `shared_ptr` 큐의 비교로 적용되는 구조가 아니므로 FIFO/예약 시간순 큐가 아니다.
`ProcessJob()`은 실행 mutex를 잡은 채 callback을 실행한다. Five는 최대 5개, Snapshot은 진입 시 크기만큼 처리하므로 같은 큐에 실행자를 늘려도 callback은 직렬화된다.
`Clear()`도 같은 mutex를 사용한다. 최적화하면서 callback 직렬화·disconnect 폐기·세대 검사·재등록·종료 수명 보장을 유지해야 한다.

`JobScheduler`의 ready 대상은 `std::priority_queue<JobTarget*>`다. 기본 비교에서 높은 주소 대상이 우선하며 대상별 Five budget만으로 공정성을 보장하지 않는다.
로비의 content worker는 현재 1개다. `CClient::ProcessUpdate()`는 이동 중 자기 작업을 즉시 다시 등록하므로 높은 주소 대상이 계속 ready 상태가 될 수 있다.
게임 `CMatch`는 Snapshot 큐를 기존 업데이트 실행 경로에서 처리한다. 게임의 `TIMER_EVENT` 큐는 별도로 존재하므로 일반 작업 큐의 순서와 예약 이벤트의 시간순 계약을 구분한다.

## 개선 순서와 회귀 조건

아래는 현재 코드와 기준 측정을 근거로 한 제안이며 아직 구현하지 않았다.

| 우선순위 | 개선 방향 | 판정/주의 사항 |
|---|---|---|
| 1 | ready 대상의 주소 우선순위를 FIFO/round-robin 방식으로 교체 | 자기 재등록 대상이 있어도 다른 대상의 작업이 실행되어야 함. ready 중복 등록·lost wakeup·disconnect 경로 회귀 |
| 2 | 로비 이동 업데이트의 즉시 자기 재등록을 tick/타이머 기반으로 제한 | idle/이동 CPU와 정지 응답 지연을 함께 비교. 이동 거리·빈도·정지 동작을 보존 |
| 3 | 일반 작업 큐의 FIFO 계약 확정 후 정렬 큐 대체·제한된 batch 검토 | 생산자와 실행 경로를 분리하되 같은 대상 callback은 직렬화. Snapshot/Five의 신규 작업 처리 경계를 명시 |
| 4 | 전역 JobMetrics의 hot atomic/시계 비용을 thread-local 집계·샘플링으로 줄이는 안 검토 | 여러 큐에서 켬/끔 차이가 큼. reporter 수명·정확도·샘플 누락·재시작을 검증하고 오버헤드 재측정 |
| 5 | 작업 할당/소유권 개선·풀링 검토 | 사전 할당만으로 일관된 개선을 확인하지 못함. 실제 할당 횟수/bytes와 working set·회수 비용부터 추가 측정 |

Five/Snapshot의 수치만으로 정책을 일괄 변경하지 않는다. batch 크기/시간 budget은 처리량과 대상별 최장 대기를 함께 비교해 선택한다.
같은 큐의 mutex를 단순 제거하거나 callback을 무보호로 병렬 실행하지 않는다. 단일 실행 소유권 방식은 재등록/소유권 해제 경합과 `Clear()`의 의미부터 설계해야 한다.
