# 스킬별 파티클 풀 5개의 필요성 검토

후속 상태: 아래는 구현 전 정적 검토와 조건부 추정 기록이다. 이후 [전체 파티클 공용 GPU 풀](PARTICLE_BUFFER_POOL.md)을 구현했다. 현재 동작·실측·한계는 후속 문서를 따른다. 이 문서의 예상 수치를 실측 결과로 바꾸지 않는다.

2026-10-05 정적 코드 검토. **모든 종류에 GPU 버퍼 5개를 미리 생성할 필요는 없다.** 현재 5는 서버가 같은 종류의 스킬 객체를 최대 5개 보관하도록 정한 상수이며, 실제 전투에서 측정한 최적 용량은 아니다. 여러 영웅의 동일 스킬과 한 영웅이 반복 발사한 투사체가 겹치는 경우에 대비한 풀이다.

이번 작업은 검토와 기록만 수행했다. 풀 크기·GPU 버퍼 생성 시점·패킷 처리는 변경하지 않았다. 아래 절감량과 개선 방향은 미구현이며, 기존 [선택 스킬 최적화의 실측 127→72개](PARTICLE_SELECTED_SKILLS.md)는 그대로 유지한다. [종류별 ID·소스 해시 근거](evidence/particle-pool-capacity-review-20261005.json)는 실행 중 동시 효과 수를 측정한 자료가 아니다.

## 5개의 의미와 버퍼 생성 비용

서버 `MAX_SKILL_OBJECT = 5`는 종류별·매치별 풀의 0~4번을 나타낸다. `CGameMgr`의 할당 함수는 첫 번째 비활성 객체를 활성화하고 해당 번호를 반환한다. 그 번호가 클라이언트에 전달되며, 클라이언트는 `skillObjectInfos[type][id]`와 `m_SkillTypeParticle[type][id]`를 연결한다. 현재 선택된 종류는 0~4번에 각각 독립된 가변 파티클 버퍼를 미리 생성한다. 다섯 영웅을 위한 버퍼가 아니며, 같은 종류를 사용하는 참가자 전체가 해당 풀을 사용한다.

영웅이 한 명이어도 이전 투사체가 살아 있는 동안 다음 투사체를 발사할 수 있다. 예를 들어 `CArcherAttack::Update`는 이동 후 충돌 결과로 제거 여부를 판단하며, 발사자의 다음 시전 가능 시점과 투사체 제거 시점이 일치하지 않는다. 같은 종류를 사용하는 영웅 수만큼 버퍼를 만들면 이 중첩을 처리하지 못한다.

동시 활성 수와 ID 범위도 다르다. 0~4번이 사용된 뒤 0~3번만 먼저 종료되면 활성 객체는 하나여도 ID는 4다. 현재 직접 인덱싱을 유지하면서 벡터를 활성 수나 선택한 영웅 수로 줄이면 해당 효과가 누락될 수 있다. **0~4번을 표현할 논리 슬롯 유지와 대형 GPU 버퍼 5개 선할당은 별개의 결정**이다.

현재 파티클 객체 하나는 최대 300,000개 파티클을 위한 두 대형 버퍼를 가진다. 이전 GPU 계측에서 두 DEFAULT heap allocation의 합계는 객체당 **18.375MiB**였다. 따라서 종류 하나의 5개 선할당은 **91.875MiB**다. 이 수치는 대형 버퍼 allocation이며 CPU 객체·텍스처·기타 버퍼나 프로세스 Private commit 전체 비용은 포함하지 않는다.

근거: [서버 상수](../../Server/Game_Server/protocol.h) 36행, [서버 할당 함수](../../Server/Game_Server/CGameMgr.cpp) `ArcherAttack` 등, [클라이언트 수신](../../Client/WarOfDimension/NetworkManager.cpp) `AddSkillObjectPacket`, [생성·렌더링](../../Client/WarOfDimension/Scene.cpp) `CIngameScene::BuildObjects` 및 `Render`의 스킬/타워 처리, [투사체 수명](../../Server/Game_Server/CArcherAttack.cpp) `Update`.

## 종류별 판단

`NumParticle(SKILL_TYPE)`에서 파티클을 사용하는 20종을 모두 대조했다. 아래 슬롯 수는 현재 패킷 ID를 그대로 인덱스로 사용할 때 필요한 주소 범위다. 실제 동시 활성 수나 최적 GPU 버퍼 수와 같다고 해석하지 않는다.

| 종류·경로 | 현재 서버 ID | 검토 결과 |
|---|---|---|
| 서버 풀을 사용하는 투사체·스킬 14종 | 첫 비활성 슬롯 0~4 | 기존 계약상 5개 논리 슬롯을 지원해야 한다. 실제 버퍼는 최초 사용 시 생성하는 개선이 적합하다. 서버 풀 자체를 줄일 근거는 아직 부족하다. |
| `ARCHER_STROM_ARROW`, `WIZARD_BIGBANG_CONTINUE` | 시전자 `GetMatchId()`, 영웅 0~2 | 현재 영웅 슬롯 기준 주소 범위는 3개다. 실제 선택한 시전자만 버퍼를 생성할 수 있지만 ID 매핑을 유지해야 한다. |
| `ARCHER_ARROW_RAIN`, `WIZARD_DARKNESS_RAY` | 모든 시전자에 0 고정 | 현재는 0번만 사용하지만 다중 시전자 충돌 문제가 있다. 올바른 용량 결정 전에 효과 ID를 분리해야 한다. |
| `PRO_SCL` | 0 고정, 보스 한 명 | 현재 경로는 1개 슬롯으로 표현된다. 나머지 4개 선할당의 사용처가 없다. |
| `TOWERATTACK` | `PATH_NUM = 4`인 타워 투사체 풀의 0~3 | 4개면 현재 경로를 지원한다. 4번 파티클 객체는 생성 후 사용되지 않는다. |

서버 풀 14종은 다음과 같다. 각 할당 함수의 반복 범위·활성화·반환 ID를 자동 대조했다.

| 직업 | 종류 |
|---|---|
| Archer | `ARCHER_ATTACK`, `ARCHER_PENETRAITING_SHOT`, `ARCHER_STICKY_ARROW`, `ARCHER_PHOENIX_ARROW` |
| Fighter | `FIGHTER_FIREBALL` |
| Swordman | `SWORDMAN_AURA_BLADE`, `SWORDMAN_JUDGEMENT_SWORD` |
| Wizard | `WIZARD_ATTACK`, `WIZARD_MAGIC_MISSILE`, `WIZARD_ENERGY_BALL`, `WIZARD_BIGBANG` |
| Ogre | `OGRE_DIMENSION_CRUSH` |
| Programmer | `PRO_ATTACK`, `PRO_RETURN_ZERO` |

직접 ID 경로의 근거는 [CArcherTimer](../../Server/Game_Server/CArcherTimer.cpp)의 StormArrow 생성/제거 180/195행, ArrowRain 225/255행, [CWizardTimer](../../Server/Game_Server/CWizardTimer.cpp)의 DarknessRay 134/145행과 BigBang 후속 제거 226행, [CBigBang](../../Server/Game_Server/CBigBang.cpp)의 후속 생성 37행, [CProTimer](../../Server/Game_Server/CProTimer.cpp)의 SCL 133/144행이다. 타워는 [CGameMgr.h](../../Server/Game_Server/CGameMgr.h)의 `m_towerAttack` 크기와 `CGameMgr::TowerAttack` 및 클라이언트 `PATH_NUM` 렌더링 범위를 함께 확인했다. 타워 투사체 ID는 빈 풀 객체 번호이며 타워 자체의 번호와 동일하다고 가정하지 않는다.

전체 20종의 현재 100개 선할당 중, 현행 ID 주소 범위만 합산하면 83개다. 하지만 이 합계는 ArrowRain/DarknessRay의 기존 0번 충돌까지 그대로 둔 계산이므로 정상적인 다중 영웅 처리의 권장 용량이나 구현 후 결과로 사용할 수 없다.

## 용량을 줄이기 전에 확인할 기존 문제

ArrowRain과 DarknessRay는 서로 다른 영웅이 시전해도 같은 종류의 0번 위치·방향·표시 상태에 기록한다. 나중 시전이 앞선 효과를 덮어쓰고, 한 시전자의 종료가 다른 시전자의 효과도 숨길 수 있는 구조다. 서버의 효과별 피해 처리가 별도로 진행되는 것과 클라이언트의 독립 시각 효과 보장은 구분해야 한다. 0번만 사용한다는 이유로 다중 시전자에게 한 개면 충분하다고 판단해서는 안 된다.

14종 서버 풀 할당 함수는 모두 빈 슬롯이 없으면 `return 0`으로 종료한다. 예를 들어 `CArcherTimer::Attack`은 반환값 `-1`만 실패로 판단하므로 풀 고갈 시에도 0번 생성 패킷을 보낼 수 있다. 풀 크기를 줄이면 이 문제를 더 쉽게 만나게 된다. 실패 값과 호출부 처리를 일치시키고, 고갈 시 생성 패킷을 보내지 않는 검증이 필요하다. 이번 검토에서는 수정하지 않았다.

쿨타임이 길거나 보스가 한 명인 스킬도 현재 0~4번 할당 계약을 가진다. 쿨타임만으로 객체 수명을 추정하거나 최대 중첩을 단정할 수 없다. `LOCAL_TEST`의 쿨타임 우회, 쿨타임 감소 효과, 실제 충돌·이동·타이머 종료 조건을 포함한 검증이 필요하다.

## 동일한 파티클의 공유 가능 범위

공유 자체는 가능하지만 공통 자원과 실행 중 상태를 구분해야 한다. 현재 `CParticleObject`는 Scene에서 만든 동일한 텍스처·난수 텍스처·Shader를 참조하므로 이 자원은 이미 공유한다. 반면 생성자마다 `CParticleMesh`를 만들고, 각 메시의 Stream Output/Draw 버퍼에는 해당 효과의 현재 입자 상태를 보관한다.

`CParticleMesh::PreRender`는 이전 Draw 버퍼를 입력으로 쓰고 Stream Output 버퍼에 다음 상태를 기록한 뒤 두 버퍼를 교환한다. 시작 여부·입자 수·출력 크기도 개별 상태다. 같은 종류라도 서로 다른 시점에 시작한 효과는 입자의 위치·속도·남은 수명이 달라질 수 있다. 이 버퍼 쌍을 같은 포인터로 연결하면 다음 효과가 앞선 효과의 상태를 덮어쓰고 갱신·카운터·재시작 처리가 섞인다. 정적 geometry의 `SetSharedMesh` 방식을 그대로 적용할 수 없다. 근거: [CParticleMesh](../../Client/WarOfDimension/Mesh.cpp)의 `CreateStreamOutputBuffer`·`PreRender`와 [CParticleObject](../../Client/WarOfDimension/Object.cpp)의 생성자·`Render`.

후속 설계로는 하나의 큰 버퍼 쌍에 효과마다 서로 다른 영역을 할당하거나, 비활성 버퍼를 GPU 사용 완료 후 다른 효과가 재사용하게 할 수 있다. 공통 할당 공간을 사용하더라도 동시에 존재하는 독립 입자의 상태 저장 공간은 필요하다. 각 효과에 여전히 300,000개씩 예약하면 자원 개수를 줄이는 것만으로 큰 메모리 절감이 생기지 않는다. 실제 입자 수에 맞춘 총 용량과 재사용 정책이 함께 필요하다.

모든 인스턴스가 같은 진행 시점·로컬 움직임을 사용하는 효과는 한 번 계산한 상태를 위치 변환만 달리해 여러 번 그리는 방식도 검토할 수 있다. 시작 시점·난수·방향·가속도 등 독립 조건이 필요한 효과는 그대로 적용할 수 없으며, 시간과 난수 seed로 상태를 계산하는 Shader 등 추가 설계가 필요하다. 현재 구현 여부나 예상 절감량으로 제시하지 않는다.

## 후속 개선 제안 — 미구현

1. **ID를 수용할 논리 슬롯은 유지하고 최초 표시 시 필요한 GPU 버퍼를 생성한다.** 종류별·ID별 독립 버퍼로 겹치는 효과를 유지한다. 네트워크 수신 스레드에서 렌더링 command list를 직접 사용하지 않고, 동기화된 상태 전달 후 렌더링 자원 생성 경로에서 처리한다. 최초 생성 지연과 업로드 완료·GPU 대기·재사용 초기화·종료 시 해제도 검증한다.
2. ArrowRain/DarknessRay의 시전자별 효과 ID와 서버 풀 고갈 처리를 개선한다. 패킷 상수·필드·packing을 유지할 수 있는 ID 할당부터 검토하고, 다중 영웅 동시 사용·서로 다른 종료 시점·고갈 시 실패 경로를 확인한다.
3. 종류별 활성 객체 최대치, 최대 사용 ID, 객체 생존 시간, 시전자 수, 할당 실패 횟수를 기록한다. 일반 전투·네 참가자 동일 스킬·연속 기본 공격·쿨타임 감소·로컬 테스트에서 확인한 뒤 서버 풀 상한을 결정한다.

최초 사용 시 생성만 적용하면 한 번 사용한 버퍼는 매치 종료까지 남을 수 있다. 매치 시작 비용은 줄지만 모든 ID가 결국 사용되면 해당 풀의 최종 비용은 기존과 같아진다. 비활성 GPU 버퍼를 더 작은 재사용 풀에 매핑하는 추가 개선은 GPU 사용 완료와 효과별 초기화를 보장하는 별도 설계가 필요하다.

## 현재 측정 조합에서 예상할 수 있는 절감량

기존 고정 조합의 9종 풀 중 8종은 0~4번 서버 풀을 사용하고, 특수 경로는 타워 한 종류다. 따라서 ID 계약을 그대로 두고 정적으로 확인한 미사용 객체만 제거하는 범위에서는 다음 한 개가 확실한 후보다.

| 항목 | 현재 실측 | 타워만 줄인 예상 — 미구현 |
|---|---:|---:|
| 종류별 파티클 객체 | 45개 | 44개 |
| 전체 파티클 객체 | 72개 | 71개 |
| 두 대형 DEFAULT 버퍼 allocation | 1,323.000MiB | 1,304.625MiB |
| 예상 allocation 감소 | — | 18.375MiB |

후속 실행 파일이나 메모리를 재측정한 결과가 아니다. 프로세스 Private commit/Working Set/DXGI LOCAL의 감소량으로 동일 수치를 주장하지 않는다. 나머지 버퍼의 추가 절감은 실제 사용 ID에 따른 생성 정책과 전투 계측으로 확인해야 한다.

## 재사용 풀의 조건별 예상 절감량 — 미구현

현재 고정 조합의 72개 중 종류별 스킬 풀은 45개, 선택 슬롯·환경 효과는 27개다. 스킬 풀만 재사용하고 각 버퍼 쌍의 300,000개 입자 용량을 유지한다는 조건으로 계산한다. Stream Output/Draw 두 버퍼를 한 쌍으로 세며, reference GPU에서 쌍당 18.375MiB allocation을 사용한다.

```text
현재 = (스킬 45쌍 + 슬롯·환경 27쌍) × 18.375 = 1,323.000MiB
예상 = (재사용 풀에 유지하는 스킬 R쌍 + 27쌍) × 18.375MiB
절감 = (45 - R) × 18.375MiB
```

| 유지하는 스킬 버퍼 쌍 | 예상 전체 대형 버퍼 allocation | 예상 절감 | 현재 전체 대형 버퍼 대비 |
|---:|---:|---:|---:|
| 9 | 661.500MiB | 661.500MiB | 50.0% |
| 18 | 826.875MiB | 496.125MiB | 37.5% |
| 27 | 992.250MiB | 330.750MiB | 25.0% |
| 45 | 1,323.000MiB | 0 | 0% |

이 표의 R은 평균 활성 효과 수가 아니라 **실제로 유지하는 물리 버퍼 수**다. 효과 종료 뒤 남는 입자, 미리 확보한 여유, GPU가 사용 중이라 반환 대기하는 버퍼를 포함한다. 종류별로 분리된 풀이라면 종류별 최대 보유 수를 합산하고, 종류 간 호환성을 보장하는 공용 풀이라면 전체 풀의 최대 보유 수를 사용한다. 게임 실행 중 계속 확장하고 축소하지 않는 풀은 과거 최대 수요만큼 메모리를 유지한다. 모든 기존 슬롯을 선할당한 채 객체만 재사용하면 절감량은 0이다.

현재 전투 최대치의 계측이 없어 어느 행을 실전 기대값으로 선택할 근거는 없다. 재사용 풀 유지량이 18쌍이면 약 496MiB 절감이라는 조건부 계산이다. 현재 GPU allocation을 단위 비용으로 사용한 추정으로, 통합 allocation의 정렬·빈 공간·관리 메타데이터·확장 중 구/신 버퍼 동시 보유는 포함하지 않는다. 전체 프로세스 Private commit·Working Set·DXGI LOCAL의 감소량으로 직접 대입하지 않는다. [계산 조건·byte 근거](evidence/particle-buffer-reuse-estimates-20261005.json)를 별도로 보존한다.

한 효과의 용량도 실제 입자 수에 맞춰 줄이면 추가 절감이 가능하다. 정점당 32byte와 두 상태 버퍼를 유지할 때 총 예약 입자 P개의 payload는 `P × 32 × 2` byte다. 실제 allocation은 새 자원 생성 시 다시 계측해야 한다. 현재 300,000개보다 얼마나 줄일 수 있는지는 종류별 입자 최대치·생성률·수명·시각 품질을 측정한 뒤 결정한다.

## 할당 영역이 부족할 때의 처리 제안 — 미구현

풀의 효과 수 부족과 한 효과의 입자 용량 부족을 따로 처리한다. 서버 스킬 객체 ID의 주소 범위는 유지하고, 해당 ID와 물리 버퍼의 연결을 별도로 관리한다. 서버 피해·스킬 처리는 시각 자원 할당 성공 여부에 종속시키지 않는다.

| 상황 | 제안 처리 |
|---|---|
| 새 효과에 줄 빈 버퍼 쌍이 없음 | 종료된 효과 중 GPU 사용 완료가 확인된 버퍼부터 재사용한다. 없으면 예산 안에서 추가 버퍼 쌍을 확보한다. 기존 활성 효과의 영역을 덮어쓰지 않는다. |
| 한 효과의 다음 입자 수가 예약 용량에 근접함 | 생성률·수명으로 다음 상태 크기를 예측해 여유가 있는 더 큰 버퍼 쌍을 준비한다. 유효 입자 상태·카운터를 옮기고 view를 전환한다. 고정 크기 자원에 예약 범위 밖 쓰기를 허용하지 않는다. |
| 예산 상한·할당 실패·확장 완료 전 포화 | 장식 입자의 새 생성량을 제한하고 핵심 공격 범위 표시를 유지하는 간소화 효과로 대체한다. 기존 입자 갱신을 우선하고 포화·실패를 기록한다. 다른 효과의 공간을 침범하거나 무제한 확장하지 않는다. |
| 확장 전 버퍼 또는 종료한 효과를 반환함 | 마지막 GPU 사용의 fence 완료 후 재사용·해제한다. 시각 효과의 종료만으로 GPU 접근이 끝났다고 판단하지 않는다. |

증설은 큰 기존 자원을 제자리에서 늘리는 작업으로 가정하지 않는다. 새 버퍼 쌍을 생성하고 필요한 상태를 복사·전환하며, 이전 자원은 GPU 사용 완료까지 보존한다. 확장 순간에는 이전·새 allocation이 함께 있어 평상시보다 메모리가 커진다. 미리 확보할 예비 공간과 전환 시 임시 비용도 예산에 넣고 프레임 중 동기 대기로 끊기지 않도록 준비한다. fence를 이용한 반환 시점 관리와 명시적인 추가 할당 원칙은 [Microsoft의 자원 수명 관리](https://learn.microsoft.com/en-us/windows/win32/direct3d12/fence-based-resource-management) 및 [D3D12 이전 안내](https://learn.microsoft.com/en-us/windows/win32/direct3d12/porting-from-direct3d-11-to-direct3d-12)를 참고한다. Upload heap ring buffer 예제는 수명 관리 원칙의 근거이며 현재 DEFAULT 파티클 버퍼의 구현 예제로 간주하지 않는다.

현재 `ParticlePostRender`는 `m_nVertices >= MAX_PARTICLES`이면 `m_bStart = true`로 되돌린다. `_WITH_QUERY_DATA_SO_STATISTICS`는 기본 비활성이며, 활성 경로도 `NumPrimitivesWritten`만 읽는다. 용량 축소 시 전역 300,000개 기준과 재시작 처리를 그대로 둘 수 없다. 효과별 실제 할당 용량·포화 처리·출력 카운터·생성 예산을 함께 변경해야 한다.

Stream Output에서 실제 출력 수와 충분한 공간이 있었다면 필요한 출력 수를 비교하면 부족 여부를 확인할 수 있다. [공식 통계 정의](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_query_data_so_statistics)의 `PrimitivesStorageNeeded > NumPrimitivesWritten`을 이용한 검출을 검토한다. 통계는 GPU 완료 후 확인하는 사후 정보이므로 이미 생략된 입자를 증설만으로 복구할 수 없다. 다음 프레임 증설과 생성량 제어에 사용하되, 이를 사전 예약·메모리 예산 검사의 대체 수단으로 사용하지 않는다. 현재 클라이언트는 자동 확장·재사용 풀·이 포화 처리를 구현하지 않았다.

## 검증과 한계

`compile_commands.json` 227개 소스와 Serena 설정을 확인하고 `serena project index-file Server/Game_Server/CGameMgr.cpp .`에서 37개 심볼 색인 성공을 확인했다. 20종 분류, 14종 풀 할당, 직접 ID 6종, 타워 서버/클라이언트 범위와 소스 10개의 SHA-256을 정적 대조했다. 문서 UTF-8·상대 링크·JSON 구문·계산·변경 줄 공백을 확인했다.

실행 코드와 측정 실행 파일은 바꾸지 않았으므로 빌드·게임 실행을 반복하지 않았다. **실전 동시 효과 최대치, 버퍼 5개의 실제 사용 빈도, 최초 사용 시 생성의 성능은 미검증**이다. 기존 [선택과 생성 흐름도](../diagrams/particle-selection/README.md)를 현재 코드와 대조했으며 구조·흐름 변경이 없어 Archify JSON/HTML은 재생성하지 않았다.
